A makeup artist (MUA) gets wedding bookings through WhatsApp and a notebook. Dates get mixed up. Payments are hard to track. I wanted a booking form that saves each booking in a place she already knows: a Google Sheet.

So I built "Booking Rapi" ("tidy booking" in Indonesian). It is the first automation for my studio project. It runs on **n8n**, a tool where you build automations by connecting boxes (called **nodes**) in a visual editor. I host n8n myself on a small **VPS** (a rented virtual server).

This post is my learning log. I wrote it so I can re-read it later and remember **why** I did each step, not only what I typed. The demo client is a fake MUA called "Aurora". No real client data is in this post.

**One-sentence answer:** A Next.js form validates the booking, sends it with a secret header to an n8n webhook behind Caddy, and n8n writes it to Google Sheets and Google Calendar, then emails a daily recap.

## What you will learn

- How to run n8n with Docker Compose so it is never directly open to the internet.
- How Caddy gives you HTTPS without extra tools, and why I picked it over nginx.
- The small security layers that matter on a one-person server: firewall, 2FA, a webhook secret.
- How to back up n8n and copy the backup to Google Drive with rclone.
- How three workflows, one Google Sheet, and one validation schema work together, plus the bugs I hit.

## The full flow

Here is the whole system before any detail. Every section below follows this picture from top to bottom.

![Architecture of the Booking Rapi automation: the visitor's booking form goes to Next.js on Vercel (valibot check), then over HTTPS with a secret header through Cloudflare DNS to a VPS. On the VPS, ufw allows only ports 22, 80 and 443, Caddy handles HTTPS on port 443 and forwards to n8n in Docker on 127.0.0.1:5678. n8n writes the booking to Google Sheets, creates a Google Calendar event and sends a daily 08:00 Gmail recap. Every Sunday at 03:00 a backup script archives the n8n data and rclone copies it to Google Drive.](/blog/booking-automation-self-hosted-n8n/n8n-booking-flow.png)

In words:

1. The visitor fills the form. The site checks the data with **valibot**, a small TypeScript validation library.
2. The Next.js API route sends the booking to an n8n **webhook** (a URL that starts a workflow when it receives a request). It adds a secret header.
3. Cloudflare DNS points `n8n.example.com` to the VPS. **Caddy** receives the HTTPS request and forwards it to n8n.
4. n8n checks the data again, checks the date, adds a row to Google Sheets, and creates a Google Calendar event.
5. A second workflow tells the form which dates are already taken. A third one emails the MUA every morning at 08:00.

A date counts as "taken" only when its status is **DP** (deposit paid) or **Lunas** (fully paid). A new booking has status **Baru** (new). It does not block the date yet.

## Step 1: Check the VPS before installing anything

My server is a Biznet GIO NEO Lite: Ubuntu 24.04, 2 vCPU, about 3.8 GiB RAM, and 4 GiB swap. I set up a VPS from zero in my [Hermes Agent part 1 post](/blog/hermes-agent-part-1-overview-to-vps-ready), so I will not repeat that here.

Before installing, I checked two things. Nothing was listening on ports 80 and 443. The firewall (ufw) was still inactive.

**Why:** Caddy needs ports 80 and 443. If another web server already uses them, Caddy fails to start. Knowing the firewall state early also tells me what I must open later.

## Step 2: Install Docker from Docker's own apt repository

**Docker** runs an app inside a **container**: a small, isolated box with everything the app needs. I installed Docker Engine and the **Compose plugin** from Docker's official apt repository. I did not use the snap package. Then I added my user to the `docker` group, so I do not need `sudo` for every command.

**Why the official repo:** it is the install path Docker documents, it gets updates through normal `apt upgrade`, and it includes the Compose plugin.

**Gotcha:** I copied a command from my notes together with the backticks around it. The shell treated the backticks as "run this and paste the result". I got `Docker: command not found`. Copy only the command itself.

## Step 3: Run n8n with Docker Compose

**Docker Compose** describes containers in one YAML file, so you can start everything with one command. This is the important part of my file.

`~/n8n/docker-compose.yml`

```yaml
services:
  n8n:
    image: docker.n8n.io/n8nio/n8n
    restart: unless-stopped
    ports:
      - "127.0.0.1:5678:5678"
    env_file: .env
    environment:
      - N8N_PROTOCOL=https
      - WEBHOOK_URL=https://${N8N_HOST}/
      - GENERIC_TIMEZONE=Asia/Jakarta
      - TZ=Asia/Jakarta
      - N8N_RUNNERS_ENABLED=true
      - N8N_DIAGNOSTICS_ENABLED=false
    volumes:
      - n8n_data:/home/node/.n8n
    mem_limit: 1g

volumes:
  n8n_data:
```

What each choice does, and why:

- **`127.0.0.1:5678:5678`** publishes n8n only on localhost (the server talking to itself). Nobody on the internet can reach port 5678. Only Caddy, on the same server, can. This also matters for the firewall: Docker can skip ufw rules for published ports (more in Step 6).
- **`restart: unless-stopped`** starts n8n again after a crash or a reboot.
- **`WEBHOOK_URL` and `N8N_PROTOCOL=https`** tell n8n its public address. Without them, n8n shows webhook URLs with `localhost`, which outside services cannot call.
- **Timezone `Asia/Jakarta`** makes "every day at 08:00" mean 08:00 in Jakarta (WIB), not 08:00 UTC.
- **Named volume `n8n_data`** keeps workflows, credentials, and the database outside the container. I can delete and recreate the container without losing data.
- **`mem_limit: 1g`** caps n8n at 1 GB of RAM. The VPS has about 3.8 GiB in total and runs other things too. If a workflow goes wrong and eats memory, only the n8n container is killed (and `restart: unless-stopped` brings it back), not the whole server.

The secrets live in a separate file, `~/n8n/.env`, with permission `chmod 600` (only my user can read it). It holds `N8N_HOST` and `N8N_ENCRYPTION_KEY`. I generated the key like this:

```bash
openssl rand -hex 32
```

**Why the encryption key matters:** n8n encrypts every saved credential (Google login, webhook secret) with this key. If you lose the key, your backup restores, but every credential inside it is unreadable. I keep a copy of `.env` in my password manager, not next to the backups.

n8n uses **SQLite** by default (a database stored in one file). For one small client, that is enough.

## Step 4: Point a subdomain to the VPS with Cloudflare DNS

**DNS** turns a name like `n8n.example.com` into a server IP address. In Cloudflare, I added an **A record** (name to IPv4 address): `n8n` → `<VPS_IP>`.

I set **Proxy status** to **DNS only** (the grey cloud), not "Proxied" (the orange cloud).

**Why grey cloud:** with the orange cloud, Cloudflare sits in the middle and serves its own certificate. I wanted Caddy to talk to Let's Encrypt directly and get a certificate for this server. DNS only keeps the path simple: visitor → my VPS.

I checked that the name resolved before moving on:

```bash
getent hosts n8n.example.com
```

## Step 5: Caddy, the reverse proxy that does HTTPS for you

This is the step I most want to remember, so here it is in simple words.

**A reverse proxy** is a web server that stands in front of your app. Think of a hotel receptionist: guests only talk to the receptionist, and the receptionist passes the request to the right room. The real mechanism: Caddy listens on the public port 443 (HTTPS). It receives each request and forwards it to n8n on `127.0.0.1:5678`. n8n never faces the internet directly.

**HTTPS** encrypts traffic between the browser and the server. It needs a **TLS certificate**, a file that proves you own the domain. **Let's Encrypt** gives these certificates for free, but they expire after a few months.

Caddy's big feature: it gets the certificate from Let's Encrypt **and renews it automatically**. No certbot, no cron job, no renewal script. My whole config is three lines.

`/etc/caddy/Caddyfile`

```text
n8n.example.com {
  reverse_proxy 127.0.0.1:5678
}
```

Line 1 says "handle requests for this domain". Caddy sees a real domain name, so it turns on HTTPS by itself. Line 2 says "forward everything to n8n".

I checked it from my laptop:

```bash
curl -I https://n8n.example.com
# HTTP/2 200
```

**Why not nginx:** nginx is great, but for HTTPS it needs a separate tool (like certbot) and more config. For one app on one server, Caddy is the simplest setup that is still correct.

**Without this step:** n8n would be plain HTTP on port 5678. Passwords and webhook secrets would travel unencrypted, and Google OAuth would refuse a non-HTTPS callback.

## Step 6: Turn on the firewall without locking myself out

**ufw** ("uncomplicated firewall") is Ubuntu's simple firewall tool. A firewall decides which ports accept connections from outside.

First, I confirmed that SSH (my remote login) listens on port 22. If I enable the firewall without allowing SSH, I lose access to my own server. Then:

```bash
sudo ufw default deny incoming
sudo ufw allow 22/tcp
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw enable
```

Port 22 is SSH. Port 80 is plain HTTP; Caddy uses it to redirect to HTTPS and for certificate checks. Port 443 is HTTPS. Everything else is closed.

**Gotcha:** Docker can bypass ufw for ports you publish. A rule like `"5678:5678"` would be public even with ufw on. My setup is safe because n8n is bound to `127.0.0.1` only (Step 3). This is the real reason for that localhost binding.

My cloud provider also offers a "Security Group" (a firewall outside the VM). I skipped it on purpose. Two firewall layers set up in a hurry can lock out SSH. One layer, set up carefully, is enough for this server.

## Step 7: Owner account and 2FA

A new n8n instance asks the first visitor to create the **owner account** (the admin). Do it early. Until the owner exists, anyone who opens the URL first could claim it.

Then I enabled **2FA** (two-factor authentication: a password plus a code from an authenticator app). Anyone who opens the n8n editor can read data and run workflows, so a password alone is not enough.

n8n also has "Enforce 2FA for all users". It is a paid feature. I am the only user, so I do not need it.

## Step 8: Backups, on the server and off the server

A backup protects you from disk failure, an accidental delete, a hack, or a problem at the provider. I set up two layers.

**What `/home/ubuntu/n8n/backup.sh` does, in order:**

1. Runs `docker run --rm alpine tar czf ...`. This starts a throwaway **alpine** container (a tiny Linux image) that mounts the `n8n_data` volume and packs it into `/home/ubuntu/n8n/backups/n8n-YYYY-MM-DD.tar.gz`. `--rm` deletes the container when it finishes.
2. Runs `find ... -mtime +28 -delete` to delete local backups older than 28 days.
3. Runs `rclone copy` to send the backups folder to `gdrive:n8n-backups` on Google Drive.
4. Runs `rclone delete --min-age 90d` to delete Drive copies older than 90 days.

**Why a throwaway container:** the data lives in a Docker volume, not a normal folder. A temporary container is the clean way to read the volume without touching the running n8n.

**Why a copy off the server:** a backup on the same disk dies with the disk. **rclone** is a command-line tool that copies files to cloud storage, so a second copy lives in Google Drive.

**Why 28 and 90 days:** the backup runs once a week. 28 days keeps the last 4 copies on the server, which is enough for a quick restore and keeps the small disk from filling up. 90 days keeps about 13 copies in Drive. If I notice a problem late, for example a workflow that broke data weeks ago, I can still go back further.

**cron** (Linux's built-in scheduler) runs the script every Sunday at 03:00, a quiet time for the server. This line is in the `ubuntu` user's crontab:

```text
0 3 * * 0 /home/ubuntu/n8n/backup.sh
```

Three gotchas from this part:

- **Connecting Google Drive on a server with no browser.** In `rclone config`, answer `n` to "auto config". Run `rclone authorize "drive"` on your laptop, which has a browser. Paste the token it prints back into the server.
- **The colon matters.** `rclone lsd gdrive` (no colon) looks at a local folder named `gdrive`. `rclone lsd gdrive:` looks at the Google Drive remote.
- **cron is not your terminal.** cron runs with a very small environment and does not expand `~` the way your shell does. So the script uses absolute paths everywhere, and calls rclone with `--config /home/ubuntu/.config/rclone/rclone.conf` so it always finds the Drive login. Then test the script as the same user that cron uses.

I chose the Drive **scope** `drive.file`. A scope is the permission level you give an app. With `drive.file`, rclone can only see files it created itself. This is **least privilege**: give a tool only the access it needs.

## Step 9: Design the Google Sheet as the client's "database"

The MUA already uses Google Sheets. So the Sheet is the database, and it must be pleasant for a human to read. The **Booking** tab has these columns (in Indonesian, for the client):

No. Booking · Tanggal Acara (event date) · Nama Klien (client name) · No. WhatsApp · Lokasi · Paket (package) · Harga (price) · DP (deposit) · Sisa (remaining) · Status · Tanggal DP · Catatan (notes) · Masuk Pada (received at)

The **Sisa** column is a formula in the header cell:

```text
={"Sisa"; ARRAYFORMULA(IF(G2:G="",,G2:G-H2:H))}
```

**ARRAYFORMULA** applies one formula to a whole column. Here it computes price minus deposit for every row that has a price.

**Why:** n8n never writes column I. The Sheet always calculates it, so the number cannot get out of sync. In n8n I append rows with the "Minimise API Calls" mode, which leaves unmapped cells empty.

I also added a colored Status dropdown, banded rows, a frozen header, the Rp currency format, and a highlight for events in the next 7 days that still have an unpaid balance.

**Gotcha:** my ARRAYFORMULA showed `#REF!`. Old values were still sitting in the cells below it, and an ARRAYFORMULA cannot write over cells that already have content. Clearing the column fixed it.

## Step 10: Google OAuth and the webhook secret

**OAuth** lets n8n act on my Google account without knowing my password. Google gives n8n a token instead. Setup in Google Cloud:

1. Enable the Sheets, Drive, Calendar, and Gmail APIs.
2. Configure the **OAuth consent screen**. "Testing" mode is fine when only your own account uses it.
3. Create a **Web** OAuth client with this redirect URI: `https://n8n.example.com/rest/oauth2-credential/callback`.
4. In n8n, create credentials for Sheets, Calendar, and Gmail.

**Expected warning:** Google shows "Google hasn't verified this app". That is normal for your own app in Testing mode. Click **Advanced**, then continue.

**The webhook secret.** A webhook URL is public. Without protection, anyone who finds it can add fake bookings. So the webhook uses n8n's **Header Auth** credential: every request must carry the header `x-webhook-secret` with a long random value (again from `openssl rand -hex 32`). The same value lives in Vercel as the environment variable `N8N_WEBHOOK_SECRET`. The site adds the header. Random visitors cannot.

I used a credential instead of an environment variable because n8n 2.x blocks `$env` access inside nodes by default (`N8N_BLOCK_ENV_ACCESS_IN_NODE` is `true`).

## Step 11: The three workflows

### 01 Booking Intake

`POST /webhook/booking-intake`

```text
Webhook (header auth)
 → Validate Booking ── invalid → 400
 → Read Bookings
 → Check Date ──────── taken → 409
 → Append Booking (status "Baru")
 → Create Calendar Event (all-day, "[Baru] Name - Package", wa.me link)
 → 200 { ok, bookingId }
```

The order is on purpose. Validation runs first, so bad data never reaches the Sheet. The date check runs before the append, so two people cannot book the same taken date. The Calendar event includes a `wa.me` link, so the MUA can open WhatsApp with one tap.

If creating the Calendar event fails, the booking is still saved and the response is still 200. The Calendar node is set to "continue on error". A missing event is easy to add by hand. A lost booking is not.

### 02 Availability

`GET /webhook/booking-availability?month=YYYY-MM`

It checks the month format, reads the Sheet, and returns the dates with status DP or Lunas:

```json
{ "bookedDates": ["2026-12-20"] }
```

The date picker on the form disables these dates. The core rule in the Code node is one line:

```js
const BLOCKING = ["DP", "Lunas"];
```

**Gotcha:** Google Sheets returns dates as **serial numbers** (days since 1899-12-30), not as text. The Code node converts them to `yyyy-mm-dd`. It also accepts dates typed by hand as text, like `20 Des 2026` or `20/12/2026`.

### 03 Daily Recap

```text
Schedule 08:00 → Settings → Read Bookings → Build Recap → Anything To Report? → Gmail (HTML)
```

Build Recap looks for three things: balances due within 7 days (H-7), new bookings waiting more than 3 days for a deposit, and next week's events. If nothing matches, **no email is sent**. That is by design. An email that says "nothing today" every morning teaches people to ignore it.

**Debugging story:** my first test sent no email. The workflow did not fail. My test row had no price, so Sisa was 0, nothing qualified, and the IF node took the false branch. The workflow was correct. My test data was not.

## Step 12: Testing with curl, and the errors that taught me something

**curl** sends HTTP requests from the terminal. I tested every response code before I trusted the form.

```bash
BASE=https://n8n.example.com/webhook-test

curl -i -X POST "$BASE/booking-intake" \
  -H "x-webhook-secret: $SECRET" -H "Content-Type: application/json" \
  -d '{"name":"Test Client","date":"2026-12-05","location":"Batam","package":"akad","phone":"6281234567890"}'
# 200 {"ok":true,"bookingId":"BK-2611-XXXX"}
```

| Case                     | Status |
| ------------------------ | ------ |
| No secret header         | 401    |
| Wrong secret             | 403    |
| Invalid input            | 400    |
| Date already DP or Lunas | 409    |
| Valid booking, free date | 200    |

Things that confused me:

- **Test URL vs production URL.** `/webhook-test/...` works only right after you click **Execute workflow**, and only for one request. `/webhook/...` works after you publish the workflow.
- **"Node does not have any credentials set" (500).** After importing a workflow from JSON, each node needs its credential selected again. Look for the warning icon on the node.
- **Publish is like a commit.** Newer n8n calls activation "Publish" and asks for a version name and description. I write them like commit messages, for example `v1.1 - input validation`.

## Step 13: Validate twice (defense in depth)

**Defense in depth** means several independent safety layers, so one mistake does not break everything.

**Layer 1: the website.** The form and the API route share one valibot schema, so the client and the server cannot drift apart. It:

- normalizes the WhatsApp number to `62…` and checks `^62\d{8,13}$`;
- requires a real `YYYY-MM-DD` date, after today in Asia/Jakarta, at most 2 years ahead;
- limits lengths (name 80, location 120, notes 500) and collapses extra spaces;
- rejects name, location, or notes that start with `=`, `+`, `-`, or `@`.

That last rule stops **formula injection**. If a cell starts with `=`, a spreadsheet may run it as a formula. Someone could type a formula as their "name". On the website, I reject it, so a real user sees a clear error.

**Layer 2: n8n.** The webhook can be called directly, without the website. So n8n validates everything again. For risky text, it adds a `'` in front, so Sheets stores it as plain text:

```js
const neutralize = (value) => (/^[=+\-@]/.test(value) ? `'${value}` : value);
```

The WhatsApp number is also written as `'62…`. Without the apostrophe, Sheets turns a long number into a number format and can show it in scientific notation.

## Step 14: Stop lying when something fails

My first API route returned `{ ok: true }` even when n8n failed. The user saw "success", but the booking was lost. Nobody knew.

Now the API route is honest:

- **503** when the webhook settings are missing on the server;
- **502** when n8n fails or does not answer within 5 seconds;
- **409** when the date is taken.

The form then shows "Gagal mengirim, coba lagi atau hubungi via WhatsApp" ("Failed to send, try again or contact via WhatsApp"), with a WhatsApp link.

**Lesson:** never swallow an upstream error with `ok: true`. An honest error is annoying. A silent data loss is much worse.

## The result

- The form on the live demo creates a row in the Sheet and an all-day event in Calendar.
- Dates with DP or Lunas are blocked in the date picker.
- The daily recap email works, and stays quiet when there is nothing to report.
- The weekly backup runs and a copy lands in Google Drive.

## What I learned

- **Bind to localhost, then put a proxy in front.** It is the simplest way to keep an app private, and it also avoids the Docker-bypasses-ufw trap.
- **Caddy removes a whole class of work.** HTTPS and renewal come for free with a three-line config.
- **The encryption key is part of the backup.** A backup without `N8N_ENCRYPTION_KEY` is only half a backup.
- **Validate at every door.** The website protects users. n8n protects the Sheet from direct calls.
- **"No output" is not always a bug.** Check your test data before you debug the workflow.
- **Fail loudly.** A fake success hides lost data.

## Recap

1. The form validates the booking with valibot and posts it to `/api/booking`.
2. The API adds `x-webhook-secret` and calls the n8n webhook over HTTPS.
3. Cloudflare DNS points to the VPS. ufw allows only 22, 80, and 443. Caddy terminates HTTPS and forwards to n8n on localhost.
4. n8n validates again, checks the date, writes to Sheets, and creates a Calendar event.
5. A second workflow returns taken dates. A third sends a daily recap at 08:00.
6. Every Sunday, the n8n volume is backed up and copied to Google Drive.
