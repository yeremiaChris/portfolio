AI tools can draft React and Next.js code in minutes. That speed is useful. It also raises a fair question:

> Do I still need frontend tests?

**Short answer:** Yes. Test for **confidence**, not **coverage**. **Coverage** means how much of your code a test run touches. A high number does not mean users are safe. **Regression** means an old bug comes back after a change. AI edits make regressions more likely, not less.

This post uses the blog on this portfolio site. The facts below match the repo today, not a wish list.

## What you will learn

- Why fast AI coding makes a small test suite more important
- What the **Testing Trophy** is and how it fits Next.js
- What **Vitest** already covers here (~300 tests)
- When one **snapshot test** is OK, and when it is not
- What **E2E** tests are, and what Playwright will cover next
- What still needs a human eye

## The real problem

Shipping faster does not remove risk. It can hide risk.

A model may rename a slug, skip a draft filter, or break a table-of-contents link. The page can look fine in preview. Users still hit a 404 or a wrong date.

Tests are the guardrail. They let you merge AI-written patches when behavior still matches what you expect.

## Testing Trophy (not the old pyramid)

The **Testing Trophy** is a testing mix from Kent C. Dodds. Think of a trophy shape. The wide middle is many cheap checks. The top is a few expensive journey tests.

| Layer                   | What it is                                                | On this site                               |
| ----------------------- | --------------------------------------------------------- | ------------------------------------------ |
| Static analysis         | Types and lint rules catch typos early                    | TypeScript, ESLint, Prettier in CI         |
| Unit tests              | Fast tests for pure logic                                 | Vitest on `lib/blog.ts` and other helpers  |
| Integration / component | A few tests where UI has real behavior                    | Only when we add interactive UI tests      |
| E2E                     | **E2E** means end-to-end. A real browser opens real URLs. | Planned with Playwright, not installed yet |

**Server Components** (**RSC**) are React components that run on the server. They ship little or no client JavaScript. Blog list and post pages here use that pattern. Testing every RSC file in isolation is slow and brittle. The trophy pushes logic into Vitest and user journeys into E2E.

## What this repository has today

Honest snapshot of the test setup:

- **Vitest** is installed. `pnpm test` runs **300** tests across **55** files.
- **Playwright** is **not** in `package.json` yet. There is no `e2e/` folder. List, detail, and 404 browser checks are the **next** step.
- There is **one** snapshot test: `lib/blog-series-headings.test.ts` writes `lib/__snapshots__/blog-series-headings.test.ts.snap`.

A **snapshot test** saves expected output to a file. The next run compares new output to that file. Here it locks heading **ids** for multi-part blog series so saved reading positions still work. That is a small, stable contract. Snapshotting every card or page layout would break on every design tweak. We skip that.

This site already runs static checks in CI. Tests add **behavior** checks on top. They do not replace the type checker.

## The blog feature under test

The blog is small on purpose. That keeps the test story clear.

| Piece                           | Where it lives                            |
| ------------------------------- | ----------------------------------------- |
| Index and featured post         | `/blog`                                   |
| Post page and table of contents | `/blog/[slug]`                            |
| MDX posts                       | `content/blog/*.mdx`                      |
| Load and filter posts           | `lib/blog.ts`                             |
| Heading ids for TOC             | `getPostHeadings` (matches `rehype-slug`) |
| RSS feed                        | `buildBlogRssFeed` for `/feed.xml`        |

## Vitest: what we test and why

`lib/blog.test.ts` is the main example. It checks user-visible rules without a browser.

Heading ids must skip fenced code and match slug rules:

```ts
// lib/blog.test.ts (excerpt)
expect(getPostHeadings(content)).toEqual([
  { depth: 2, text: "Hello World", id: "hello-world" },
  { depth: 3, text: "Nested code and link", id: "nested-code-and-link" },
]);
```

Draft posts must not leak in production:

```ts
// lib/blog.test.ts (excerpt)
vi.stubEnv("NODE_ENV", "production");
expect(getPost(DRAFT_SLUG)).toBeNull();
expect(getAllPosts().some((post) => post.slug === DRAFT_SLUG)).toBe(false);
```

High-value targets in `lib/blog.ts`:

- **`getAllPosts` / `getPost`**: slugs resolve; unknown slugs return `null`; drafts respect `NODE_ENV`
- **`getPostHeadings`**: TOC anchors stay stable
- **`formatBlogDate`**: bad dates do not crash the UI
- **`buildBlogRssFeed`**: XML escapes text; items link to `/blog/[slug]`

We do **not** unit-test the full MDX render pipeline. We trust `next-mdx-remote` and plan to assert HTML through E2E later.

## What we skip on purpose

- Snapshot every component or page
- Assert CSS class strings
- Chase a coverage percentage goal
- Re-test third-party markdown or syntax highlighters

Those tests cost time and still miss slug and draft bugs.

Most blog UI (`BlogPostCard`, `FeaturedPost`) is presentational. Component tests wait until something has clicks, keyboard behavior, or state worth locking.

## Planned E2E with Playwright (not done yet)

**Playwright** is a browser test runner. When we add it, specs will live in `e2e/*.spec.ts`, not next to `app/` routes.

A thin smoke suite should cover:

1. `/blog` loads and shows at least one post title
2. Open a post and land on `/blog/[slug]`
3. The detail page shows the title and article body
4. An unknown slug shows the custom 404
5. Optional: `/feed.xml` returns RSS with a known title

Why E2E here? List and detail pages are Server Components backed by files on disk. Routing, `notFound()`, and rendered HTML are what a browser test sees best. Unit tests already guard `lib/blog.ts`. E2E guards the wire between app, MDX, and layout.

## Working with AI on tests

When you ask an AI to add tests, be specific about **behavior**:

- "Fail if a draft slug appears when `NODE_ENV` is `production`."
- "Keep heading id `hello-world` for this markdown sample."

Avoid "test the component" with no user story. That often produces brittle tests on implementation details.

AI can draft Vitest cases quickly. You still review assertions. Wrong expectations encode wrong product rules.

## What humans should still check

Tests do not replace design judgment.

- Visual design: spacing, type, motion
- UX feel: scroll, focus, loading states
- Copy tone and clarity
- Accessibility spot checks: keyboard, labels, contrast on key flows

Use CI for logic. Use your eyes for polish.

## Recap

- AI speeds up code. Tests speed up **trust**.
- Prefer the Testing Trophy: static checks, Vitest on logic, few E2E journeys.
- This repo: **300** Vitest tests, **one** targeted snapshot, **no** Playwright yet.
- Next step: Playwright for blog list, post detail, and 404.
- Tell AI what behavior to protect. Keep human review for design and feel.

Frontend testing in 2026 is not about more files. It is about a small set that catches the failures users would actually notice.
